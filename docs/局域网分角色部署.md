# 局域网分角色部署说明

让「一台有 Claude 账号的中心机」把 Claude 能力共享给局域网里的多台开发机：
**重活（gradle/git/adb 等）各机器本地跑，AI 能力由中心机统一提供。**

---

## 一、三种部署角色

通过「设置 → 中心 Claude 代理（局域网共享）→ 部署角色」选择，或用环境变量 `ROLE` 覆盖。
**优先级：环境变量 `ROLE` > 配置 `role` > 默认 `standalone`。改后需重启网关。**

| 角色 | 挂载的接口 | 适用 |
|------|-----------|------|
| `standalone`（默认） | 全部（server + node 都挂） | 单机全功能，行为与以前一致 |
| `server` | 挂 `/api/claude-proxy`、`/api/distributed`、`/api/admin` | 中心机：提供 Claude 能力 + 分布式编排 + 管理后台 RBAC |
| `node` | 只挂 `/api/devbench`、`/api/executor`、`/api/devices`、`/api/report` 等开发工具 + 后台(定时/飞书/TB监控) | 开发机：本地执行 + 被中心驱动 |

> `server` 角色不会启动 定时任务/飞书/TB 监控（那些是 node 功能）。

---

## 二、两条能力链（叠加使用）

### 阶段0：中心 Claude 做「文本任务」（已可用）
适用于**非 agentic 的文本任务**：周/月/季/年报告、TB 分析、摘要、规划等（prompt 进、文本出，不在远端读写文件）。

- **中心机**（`server` 或 `standalone`）：设置里开「① 本机作为中心 → 对外提供 Claude 文本代理」，设一个 **访问 Token**。
- **开发机**（`node`）：设置里开「② 本机作为远端 → 文本任务转发到中心」，填 **中心机地址**（`http://中心IP:网关端口`）+ **同一 Token**；把「默认引擎」选为 **中心 Claude 代理**。
- 之后开发机点「📝 总结」等文本功能，实际由中心机的 Claude 出文本；gradle/git 仍在开发机本地。

> **代理后端二选一（设置 → 中心 Claude 代理 → 代理后端）：**
> - `订阅 Claude CLI`（默认）：用中心机本机的 `claude` CLI（订阅登录）。**不转发凭证、不反代 API**，对 Anthropic 而言是单机单号官方 CLI；但「一号多人用」属个人使用条款灰色地带，量大可能触发滥用检测。
> - `Anthropic API`（合规）：填 `Anthropic API Key` 后改走官方 Messages API 按量计费，单账号多人服务合规、风险基本归零。**选了 api 但没填 key 会自动回落 cli。**

### 阶段1：中心大脑驱动「远端改代码」（基础已就绪）
适用于 **agentic 任务**（Claude 要读/改远端工程文件、跑命令）：

- **开发机**（`node`）：设置里开「③ 本机作为远端执行器」+ Token。本机暴露 `/api/executor`，
  中心可在本机**白名单工程内**执行 读/写/编辑/列目录/bash（沙箱 + 路径不越界）。
- **中心机**（`server`）：配置 `remoteExecutors`（已知开发机列表 `{name,host,token}`），
  通过 `/api/distributed/run` 让「大脑（API 引擎）」推理 + 工具转发到目标开发机执行。
- ⚠️ 大脑须是 **API 形态的 tool-use 引擎**：
  - 现成路线：启用一个 **OpenAI 兼容引擎**（Qwen/Kimi/DeepSeek/OpenAI，需对应 API Key）作大脑；
  - 想用 **Claude 当大脑**：需 Anthropic API Key（CLI 订阅无法远程驱动工具）——后续可加 Anthropic 引擎适配。

## 三、典型部署步骤

### 中心机（有 Claude 账号那台）
1. 正常装好网关（桌面版或源码）。确保已 `claude login`。
2. 设置 → 部署角色 = **服务端**（或留 standalone 也行）。
3. 开「对外提供 Claude 文本代理」+ 设 Token（如 `lan-2026`）。
4. （阶段1 可选）配置 `remoteExecutors` 指向各开发机；启用一个 OpenAI 兼容引擎作大脑。
5. 重启网关。记下中心机局域网 IP + 端口（默认 `3001`）。

### 各开发机（客户端节点）
1. 装好网关。设置 → 部署角色 = **客户端节点**。
2. 开「文本任务转发到中心」+ 填 `http://中心IP:3001` + Token `lan-2026`；默认引擎选「中心 Claude 代理」。
3. （阶段1 可选）开「本机作为远端执行器」+ 设 Token，让中心能驱动本机工程。
4. 重启网关。照常用 devbench 故事点开发、跑 gradle（都在本机）；AI 文本任务走中心。

## 四、验证

中心机（server 角色）：
```
GET  http://中心IP:3001/api/claude-proxy/health   → {ok:...}        # 应可访问
GET  http://中心IP:3001/api/devbench/tabs           → 404            # node 路由未挂（符合预期）
```
开发机（node 角色）：
```
GET  http://本机:3001/api/devbench/tabs             → 200            # 开发工具可用
GET  http://本机:3001/api/executor/health           → {ok,enabled,allowedRoots}
GET  http://本机:3001/api/claude-proxy/health       → 404            # server 路由未挂（符合预期）
```

## 五、端口 / Token / 安全

- 网关默认端口 `3001`（桌面版同）。多角色在不同机器，端口可都用 3001。
- **Token**：claude-proxy 与 executor 各有访问 Token，中心与开发机必须一致；防局域网内未授权调用。
- **executor 白名单**：只允许操作本机「应用市场工程配置」里的工程 + 克隆目录；文件路径不得越出工程根。
- `run_bash` 是本机命令执行，**仅在可信局域网开启**；后续可加命令审计/白名单。
- 建议绑内网网段 / 防火墙限制来源 IP。

## 六、能力边界（务实路线现状）

- ✅ **可分开部署**：server 与 node 用同一份代码、按角色起成两个独立部署（零文件搬动、不碰原生模块/打包）。
- ✅ **文本任务共享 Claude**：开发机不装 Claude 也能用中心机的 Claude 出报告等文本。
- ✅ **远端执行器就绪**：中心可安全驱动开发机工程内的工具（沙箱/白名单/鉴权）。
- ⏳ **agentic 完整闭环**：需启用一个带 Key 的 API 引擎作大脑（或后续加 Anthropic 引擎让 Claude 当大脑）。
- ⏳ **物理拆分 server/client 目录**：见 `docs/devbench/step2_wlan/plan_2_restructure.txt`，等真有需要时再做。
- ✅ **管理后台 RBAC**：已落地，见下「七」。

## 七、管理后台 RBAC（角色鉴权）

顶部导航「管理后台」（与「工程开发」平级），挂在 **server / standalone** 角色下（`/api/admin`）。
进入需鉴权，提供三种登录方式，统一签发后台 token（随机串，内存存储，24h 过期）。

### 1. 身份与成员从哪来——用 Teambition 用户态，零管理员权限

> 公司**钉钉**通讯录接口（OAPI `user/list`、`unionId→userid` 映射）都需要**应用级通讯录权限**，得公司管理员建应用并授权。
> 为避免这道门禁，成员与身份**改走 Teambition 用户态 Cookie**——也就是你在 TB 里 @ 同事时背后那个接口，
> 读的是**你登录用户本来就有权看到的组织架构**，无需任何管理员/应用权限。

- 成员列表：`GET /api/organizations/{orgId}/members`（用 `设置 → Teambition` 的 Cookie），返回全员 `{uid=TB _userId, name, avatar}`。
- 管理员名单存本地 `admin_users` 表，主键就是 **TB `_userId`**。
- 前置条件**仅一个**：设置里有有效的 TB Cookie（项目已有的一键登录即可）。

### 2. 三种登录方式

| 方式 | 谁用 | 机制 | 需要什么 |
|------|------|------|---------|
| **超管验证码（TOTP）** | 超管 | Google Authenticator 动态 6 位码（RFC 6238，纯 crypto 实现） | 首次扫码绑定，密钥存 `gateway/.secrets/admin-totp.json`（不进 git） |
| **Teambition 登录**（主联合登录） | 已被设为管理员的同事 | 读本机 TB 登录态 `/users/me` 得 `uid` → 比对名单 | 本机已登录 TB + 被超管加入名单 |
| **钉钉扫码**（可选，默认隐藏） | —— | OAuth2 扫码→unionId→企业 userid | **需公司开钉钉应用 + 通讯录权限**，配齐 AppKey/Secret 才显示 |

> **超管 TOTP 绑定/重置**：登录框点「首次使用 / 重新绑定验证器」，用 Authenticator 扫码或手输密钥绑定，之后用 App 的 6 位码登录。
> 密钥首次访问自动生成并存入 `gateway/.secrets/admin-totp.json`（已 gitignore）；**绑定成功后，密钥/二维码只在网关本机可见**，远程不再返回（防泄露）。丢手机用本机「重新生成密钥」重绑。

> **TB 登录与钉钉扫码"效果一样吗"**：机制一样（联合身份→比对名单→发 token），但**身份域不同**。
> 现在名单主键是 TB `_userId`，所以**能对上号、真正生效的是 TB 登录**；
> 钉钉扫码产出的是钉钉 userid，与 TB 名单对不上，只有"公司开了钉钉应用、成员源也换成钉钉"时才有意义——故默认隐藏。

### 3. 多个登录态会冲突吗？退出怎么退？

- **不冲突**。这里要分清两层：
  1. 你的 **TB / 钉钉账号登录态**（Cookie / 客户端）——那是**身份来源**，一直都在；
  2. **管理后台的 token**——你点"账号密码登录"或"Teambition 登录"后才签发，**同一时刻只有一个**，存于浏览器 `localStorage.admin_token`。
- 你"又扫码登录了 TB、又用超管账密登录后台"——这俩不在一个层面：前者是身份来源，后者是后台 token。**后台以你最后一次登录为准**；想要最高权限就用**超管账密登录**（超管 > 普通管理员）。
- **退出登录**：只吊销**当前后台 token** 并清掉 `localStorage`，**完全不影响**你的 TB / 钉钉登录态。
  例：你用超管登录后台 → 退出 → 只是退出后台，TB 账号照样登着，可以马上改用"Teambition 登录"再进。

### 4. 权限模型（super vs admin）

| 操作 | 超级管理员 super | 普通管理员 admin |
|------|:---:|:---:|
| 进入管理后台 | ✅ | ✅ |
| 查看管理员名单 | ✅ | ✅（只读） |
| 拉取组织成员 / **新增管理员** / **移除管理员** | ✅ | ❌ 403 |

> **普通管理员不能新增/移除其他管理员**——增删管理员是超管专属（后端 `/members`、`POST/DELETE /users` 均限 `super`，前端对应 UI 也仅超管可见）。

### 5. 相关配置（设置 → 管理后台）

- **超管登录 = TOTP**：无需配账密；密钥文件 `gateway/.secrets/admin-totp.json`（不进 git）。在「管理后台」登录框绑定验证器即可。
- **钉钉扫码登录回调地址**：仅当走可选的钉钉扫码方式时需要，须与钉钉后台白名单一致；TB 登录不需要。
