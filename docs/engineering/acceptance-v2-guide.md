# AIEfficiency 轻量生产验收方案 v2

## 1. 为什么旧规则会慢

旧规则把四类不同目的混在一次流程中：开发自检、故事点交付、生产发布、缺陷知识沉淀。结果是每次局部变更都被要求执行 release 构建、设备/AppMock 场景、完整证据、独立子代理和双 PASS；验收发现任何问题后又进入修改，再从头执行全流程。

真正导致时间放大的不是“测试太多”本身，而是缺少以下边界：

1. 没有 QUICK / STANDARD / RELEASE 分层；
2. 没有区分当前改动引入的问题与基线已有问题；
3. 验收者同时承担审查、修复和再次验收，职责互相污染；
4. 没有候选快照和门禁依赖图，任何补丁都让全部证据失效；
5. 没有最大修复轮数，容易陷入机会主义清理；
6. 回归测试、保护和台账对所有缺陷一刀切，低风险问题成本过高；
7. Git 安全检查按每个命令重复，而不是按工作区状态变化触发。

## 2. 新流程

```text
开发/修复
  ↓
QUICK（频繁、局部、失败快速返回）
  ↓ 候选稳定
STANDARD（普通故事点最终交付）
  ↓ 明确准备上线或命中高风险
冻结 Release Candidate
  ↓
RELEASE（最终制品 + 关键路径 + 独立只读复核）
  ↓
READY / BLOCKED
```

核心变化：完整 RELEASE 只对最终冻结候选执行一次。若发现阻断缺陷，先做最小修复，再按门禁依赖关系只重跑失效部分；只有高风险边界或制品链路发生变化才重跑完整 RELEASE。

## 3. 模式选择示例

| 用户意图/改动 | 模式 | 说明 |
|---|---|---|
| “开发完先自测一下” | QUICK | 定向检查，不声明可生产上线 |
| “验收这个普通故事点” | STANDARD | 受影响测试、构建和关键 smoke |
| “验收并自动修复” | STANDARD + 最多 2 轮修复 | 只修当前差异引入的阻断项 |
| “准备上线生产” | RELEASE | 冻结候选、最终制品、关键生产路径、独立复核 |
| 文档/文案/纯样式 | QUICK | 无行为变化时不做完整构建 |
| 认证、数据库迁移、自动更新、签名、部署 | RELEASE | 自动升级高风险门禁 |

## 4. 缺陷处理规则

### 当前交付必须修

- 当前差异引入的回归；
- 明确验收标准失败；
- 构建、目标测试、关键 smoke 或生产启动失败；
- P0/P1 安全、权限、数据损坏、错误制品、不可恢复升级问题。

### 当前交付不自动修

- 基线已经存在且未被当前差异放大的问题；
- 与任务无关的重构、性能优化或代码风格建议；
- 证据不足的推测；
- P3 级别问题。

这些问题可以进入 backlog 或回归台账，但不能让当前 Agent无限扩展任务范围。

## 5. 门禁失效与复用

推荐为每个门禁保存最小证据清单：

```yaml
candidate:
  base: <sha>
  head: <sha>
  diff_hash: <hash>
  dependency_hash: <hash>
  config_hash: <hash>
  environment: <id>
gate:
  id: G2-targeted-tests
  command: <exact command>
  result: PASS
  artifact_hash: <optional>
  started_at: <timestamp>
  finished_at: <timestamp>
```

复用原则：相同候选输入、相同命令、相同依赖和相同环境的 PASS 可以复用。修复某个文件后，只失效读取该文件或依赖其产物的门禁。

示例：

- 仅修改前端文案：重跑前端静态检查和目标 UI smoke，不重跑 gateway 集成测试；
- 修改 gateway API 响应：重跑 gateway 测试、前后端契约检查、受影响构建和关键 smoke；
- 修改签名/打包配置：重建最终制品并重跑安装、启动和关键 RELEASE；
- 修改公共协议/SDK：重跑所有消费者相关门禁。

## 6. 子代理使用策略

子代理不是“越多越安全”。建议：

- QUICK：0 个；
- STANDARD：通常 0 个，证据冲突或跨模块时 1 个只读审查者；
- RELEASE：1 个只读独立审查者；只有确实可并行且互不写冲突时再增加。

子代理只做读、审查、测试结果分析或隔离验证；主工作区始终只有一个写入者。

## 7. 与 CI 的边界

AGENTS/Skill 决定“应该运行什么、何时阻断、如何报告”；脚本/CI 负责“确定性执行”。应逐步把以下内容固化为仓库命令：

- changed-files / impacted-modules 计算；
- lint、typecheck、unit、integration、build、package、smoke；
- 候选与证据 manifest；
- 结果缓存和门禁失效；
- 最终制品哈希、签名、启动和升级检查。

不要让 Codex 每次临时猜命令；命令映射一旦稳定，应写入脚本或 CI。

## 8. 迁移步骤

1. 用本包 `AGENTS.md` 替换当前根规则；保留模块特有规则到对应子目录。
2. 将 `.agents/skills/story-acceptance-protocol/` 加入仓库。
3. 将 `.codex/agents/acceptance-reviewer.toml` 加入仓库，作为 RELEASE 独立审查者。
4. 使用 `PROMPT_apply_acceptance_v2.md` 让 Codex 扫描真实工程，建立“路径 → 风险 → 门禁命令”映射。
5. 先对 3 类历史任务回放：低风险 UI、普通后台功能、高风险发布/升级；比较耗时、漏检率和重跑次数。
6. 稳定后把关键门禁下沉到 CI，AGENTS 只保留策略。

## 9. 上线判定

- QUICK `PASS`：代码局部自检通过，未评估生产上线；
- STANDARD `PASS`：普通故事点交付通过，未完成完整生产发布门禁；
- RELEASE `PASS`：最终候选、制品、环境、关键路径和独立复核均通过，可输出 `READY`；
- 任何模式存在阻断项或证据不一致：`BLOCKED`；超过两轮自动修复必须停止。
