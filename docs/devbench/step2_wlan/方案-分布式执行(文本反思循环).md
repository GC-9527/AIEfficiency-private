# 方案：分布式执行 —— 文本反思循环（服务端 Claude 出脚本 + 客户端执行 + 结果回灌）

> 目标：让**没有 Claude 账号的客户端**借用**服务端的订阅 Claude** 做 agentic 开发（思考在服务端、执行在客户端），且**规避封号**、支持**多服务端/多客户端/随时切换**。

## 一、为什么这样能规避封号

封号高危项是**凭证共享 / 反向代理**（把 token 发给客户端、或把 `api.anthropic.com` 暴露给多客户端直连）。本方案：

- **客户端全程零接触 Claude**：拿不到任何凭证，不直连 Anthropic。
- **所有面向 Claude 的流量都来自服务端这一台、同一订阅号、官方 CLI**——从 Anthropic 视角就是"一个开发者用 Claude Code 写脚本"。
- 因此**不触发"凭证泄露/反代"这条秒封线**。
- 残余风险只剩"一个订阅号服务全队、高自动化量"的**政策/滥用灰区**（比反代低一个量级），用 **限并发(maxConcurrent) + 每日 token 额度** 压制。

Claude 能否这样做：**能**。根据上下文生成脚本就是 Claude Code 的日常用法；Claude 不知道也不关心上下文来自另一台机器。

## 二、架构与复用

```
客户端(node)                          服务端(server, 订阅 Claude)
┌───────────────────────┐            ┌──────────────────────────┐
│ devbench 故事点         │            │ claude-proxy(文本,订阅CLI) │ ← 大脑(无状态)
│  · 会话历史(本地持有)    │ ──上下文──▶ │  prompt(历史+上下文+上次结果)│
│  · 网关编排循环         │ ◀──脚本──── │  → 生成下一个脚本           │
│ executor(沙箱执行)      │            │ maxConcurrent 信号量(算力)  │
│  · 跑脚本/gradle/git/adb│            └──────────────────────────┘
└───────────────────────┘
```

复用已有：
- **claude-proxy.js**（订阅 CLI 流式文本，已有限并发+额度）= 大脑。
- **executor.js**（客户端沙箱执行 读/写/编辑/列目录/bash，白名单不越界）= 执行。
- **discovery / ServerSelect**（选服务端、算力、满载禁选）= 连接管理。
- 新增：**网关编排器**（reflection loop）+ **客户端↔服务端任务通信**。

## 三、文本反思循环（核心流程）

```
1. 客户端故事点发起任务：收集 任务 + 本机上下文(环境/相关文件/报错) + "机器C标记"
2. 客户端网关 → 当前所连服务端：发【完整相关上下文 + 会话历史(或滚动摘要) + 上次执行结果】
3. 服务端 claude-proxy 无状态调用 → 生成【下一步脚本/动作/意图】(文本)
4. 客户端网关解析脚本 → executor 执行(本机) → 捕获输出
5. 输出回灌：作为"上次结果"进入下一轮(回到 2)，直到 Claude 标记完成
6. 全程对话/结果存在客户端(该故事点 transcript)
```

- 失败/异常 → 把报错回灌让 Claude 改（反思）。
- 安全：脚本执行受 executor 白名单约束；危险命令可加确认。

## 四、会话状态模型（关键）

**客户端持有会话历史；服务端 Claude 无状态、每轮靠客户端回放上下文"还原会话"。**

| 维度 | 设计 |
|------|------|
| 会话历史存哪 | **客户端**（每故事点一份 transcript，本地）。与"工作总结归客户端"一致。 |
| 服务端 Claude | **无状态推理函数**：`(历史+上下文+上次结果) → 下一个脚本`。**不用 `--resume`**（会话绑某台服务端，换机即丢）。 |
| 跨服务端记忆 | **不共享，也做不到**（各服务端不同订阅号，CLI 会话本地绑账号）。不依赖服务端侧记忆。 |
| 服务端间复制的 | 只有**共享配置**(仓库/车型/关键词)，**不是对话历史**。 |
| token 压制 | 客户端维护**滚动摘要**（v1 先全量回放保正确；后续接本地 LLM 压缩=方案B）。 |

## 五、多服务端 / 多客户端 / 切换

- **一客户端连多服务端、某刻只连一台**：`claudeProxyClient.host` 同时只指一台，ServerSelect 切换；**任务中也能换**（状态在客户端，下一轮带全量上下文给新服务端即可）。
- **一服务端连多客户端**：claude-proxy `maxConcurrent` 信号量并发到上限、超了排队；**每次调用独立(无每客户端会话态)→ 多客户端零串扰**；算力(空闲槽)即"还能同时接几个客户端任务"。
- **满载**：客户端 `/select` 选满的返回 409；全无算力 → devbench 弹窗提示。

## 六、方案 B（可选增强：客户端本地开源 LLM）

在硬件够的客户端自动装 **Ollama + 按硬件分级的代码模型**（低端自动降级回纯执行器）。本地 LLM 职责：
- **压缩本机大上下文**后再发服务端（省 token/降延迟）；
- 把服务端的"高层意图"**落地成本机命令 + 安全校验**；
- 简单重试/格式化结果；服务端满载/断连时**离线兜底**。
- "自主训练"现实为 **RAG/few-shot**（团队知识库），非真微调。

自动安装复用现有"环境诊断/一键装"机制（Ollama 走 winget/安装包 + `ollama pull`）。

## 七、分阶段实现

1. **编排器内核**：网关 reflection loop（claude-proxy 出脚本 → executor 执行 → 结果回灌），单客户端单服务端跑通。
2. **会话状态**：客户端 transcript 持有 + 全量回放；接入 devbench 故事点（无本地 Claude 时走此路）。
3. **多端协调**：复用 discovery/ServerSelect；任务中切服务端；多客户端并发(信号量)。
4. **token 压制**：滚动摘要。
5. **（可选）方案 B**：本地 LLM 自动装 + 分级降级 + 上下文压缩。

## 八、风险与取舍

- **封号**：高危项已避开；残余政策/量风险用 限并发+每日额度 压制（已有机制）。
- **稳定性**：盲生成脚本不如 Claude 原生工具循环稳 → 靠**结果回灌反思循环**补 + 把相关文件塞进上下文。
- **token 成本**：全量回放偏高 → 滚动摘要 / 本地 LLM 压缩。
- **延迟**：每轮一次 LAN 往返 + 一次 Claude 调用；agentic 多步累加（局域网可接受）。
- **方案 B 负担**：本地 LLM 大下载/吃 RAM/无 GPU 慢 → 分级 + 低端降级。
