● 可行，这是个成熟的思路——「把 agent 拆开：大脑（LLM）在中心，手脚（工具执行）在远端」。但有一个根本约束必须先说清楚，它决定了方案怎么落地。

  核心约束：Claude Code CLI 是「大脑+手脚一体」的，拆不开

  Claude Code CLI 自己跑 LLM 推理并且自己执行工具（Read/Write/Bash/gradle…都在它所在的机器、它的进程里）。所以你没法让「Claude CLI
  的脑子在我这、它的工具在你那」——它的工具只会动它本机的文件。

  ▎ 推论：要做「中心 Claude + 远端执行」，就不能用 Claude Code CLI 跑这些远端会话，而要用 Claude 的 API（Anthropic Messages tool-use）自己写 agent
  ▎ 循环，把工具调用转发到远端执行。代价是：放弃 Claude Code CLI 那套开箱即用的强工具/规划能力，工具得你自己实现（项目里 api-tools.js 是个起点，但比 Claude Code 的工具集小）。

  你这套架构里已有的三块积木

  1. 网关本身就是「本地执行器」：设备发现/adb/git/gradle/文件操作/分支 stash/克隆……这些纯脚本工具早已在网关本机跑。
  2. WebSocket 双向通道：现成，可做中心↔远端 agent 通信。
  3. API 引擎 + api-tools（tool-use 循环）：就是「LLM 决策→调工具→拿结果→再决策」这个循环的现成范式（目前用于 Qwen/Kimi 等 OpenAI 兼容引擎，Claude 目前只走 CLI、没走 API）。

  推荐方案：拆分式 agent（中心大脑 + 远端执行器）

  中心机（有 Claude 账号）                远端 LAN 开发机（工程在这）
  ┌─ Claude 大脑(Anthropic API, tool-use)   ┌─ 执行器 agent
  │   收到「远端 X 的推理请求 + 上下文」      │  · 纯脚本任务(gradle/git/adb/文件) 本地直接跑，不碰 Claude
  │   Claude 决定要调的工具 ──WS──────────▶ │  · 收到中心来的工具调用 → 本地执行 → 回传结果
  │   拿到结果 → 继续推理 → 直到完成 ◀──────│  · 把机器环境/文件内容/命令输出 作为上下文上送
  └─ 一个账号，跨远端排队调度               └─ 路径沙箱 + 鉴权

  关键点正合你的直觉：
  - 大量工具不需要 AI（gradle 构建、git、adb、扫设备、读写文件）→ 全在远端本地跑，根本不经过 Claude。只有「需要推理/写代码决策」那几步才回中心 Claude。
  - 这样 gradle 的 CPU/内存压力都落在各自机器，中心机只扛「Claude 推理」这点轻负载。

  分阶段落地（先不写码，先认方案）

  - 阶段 0（最大性价比、最低风险）：让每台 LAN 机跑自己的网关（项目本就支持的团队模式）→ 纯脚本（gradle/git/克隆/设备）全在各自机器本地。中心机只负责出 Claude。这一步就把最重的 gradle
  全卸到各自机器了。
  - 阶段 1（实现你说的核心）：中心加一个 Claude-API agent（tool-use）；远端网关暴露「工具执行端点」；中心 Claude 的工具调用经 WS 路由到对应远端执行、回传。配套鉴权 token +
  路径沙箱（远端会执行中心发来的命令，必须防越界/防破坏）。
  - 阶段 2：中心账号的调度/排队（一个账号有速率上限，多远端同时要推理会在这排队——但纯脚本不占用它）；日志/可观测。

────────────────────────────────────────────────
一、目标与边界
────────────────────────────────────────────────
目标：
  1) 重活（gradle/git/adb/克隆/设备/文件）全部在「各自机器的本地网关」跑，中心机不再扛执行。
  2) 团队只共享「中心机的 Claude 账号」，且仅用于【非 agentic 的文本任务】。

本阶段做什么（✅）：
  - 周报/月报/季度·年度绩效报告生成（文本 in → 文本 out）
  - TB 任务分析、Bug 分诊文本、内容/日志摘要
  - 规划文本、答疑、commit message 生成
  这些都是「给 prompt、要文本」，不需要在远端机器读写文件或执行命令。

本阶段不做什么（❌，留阶段1）：
  - Claude 要读/改远端工程文件、跑命令的 agentic 编码任务。
    原因：Claude Code CLI 大脑+手脚一体拆不开；agentic 远端执行需「中心 LLM + 远端工具协议」，
    是更大的改造（见 plan_1）。本阶段这类任务仍各机器本地（各自有 Claude）或暂不支持。

────────────────────────────────────────────────
二、总体架构
────────────────────────────────────────────────
  中心机（有 Claude 账号 / 登录）
    └─ Claude 文本代理服务（claude-proxy）
         · 暴露 HTTP/SSE 端点，接收远端「文本任务」请求
         · 内部用本机 Claude 跑（claude -p 非交互，复用订阅登录）
         · 队列 + 最大并发限制（一个账号有速率上限）
         · 流式把 token 回传

  远端 LAN 开发机（工程在这，自己跑网关 localhost:3001）
    └─ 本地网关（现有，团队模式）
         · 故事点 / 工程 / gradle / git / adb 全本地执行 ← 阶段0 重点
         · 引擎新增一种 "claude-proxy"：需要 Claude 文本任务时，
           不在本地跑 claude，而是 HTTP/SSE 调中心 claude-proxy，
           再把流式结果经本地 WS 推给本地前端（体验与本地一致）

数据流：
  远端前端 → 远端网关(文本任务) → HTTP/SSE → 中心 claude-proxy → 本机 claude -p
          → 流式回 → 远端网关 WS → 远端前端

三、阶段0：执行下沉（基本零代码，靠部署 + 配置）
────────────────────────────────────────────────
  - 每台 LAN 机各装/各跑自己的网关（项目「团队模式」本就支持：UI/Skills 可来自云端或本地，
    CLI 引擎走本机）。→ gradle 等重活天然落在各自机器，互不抢中心资源。
  - 中心机除了正常使用，额外开启 claude-proxy 角色（见下）。
  - 远端网关把「Claude 引擎」指向中心 claude-proxy（文本任务）。

────────────────────────────────────────────────
四、中心 claude-proxy 设计
────────────────────────────────────────────────
端点（中心机网关新增）：
  POST /api/claude-proxy/run
    body: { requestId, clientId, prompt, system?, maxTokens?, stream?:true }
    鉴权: Authorization: Bearer <LAN_TOKEN>（仅局域网 + token）
    返回: SSE 流（event: chunk {delta} / event: done {usage} / event: error {message}）
  GET  /api/claude-proxy/health  → { ok, busy, queueLen, maxConcurrent }

中心实现（services/claude-proxy.js）：
  - 调本机 Claude：claude -p "<prompt>" --output-format stream-json
      （-p 非交互、复用中心订阅登录，无需 API key；stream-json 可流式解析 token）
      可选：若中心配了 Anthropic API key，则走 API（更可控），二选一。
  - 队列：FIFO + 最大并发 N（默认 2~3，按账号速率定）；超出排队，避免 429/限流。
  - 只做「单轮文本」：不开工具、不读写文件（cwd 用临时目录，prompt 自包含数据）。
  - 超时 + 失败回传 error，远端可降级（提示「中心 Claude 忙/不可用」）。

配置（中心 gateway/config）：
  claudeProxy: { enabled:true, token:"<LAN_TOKEN>", maxConcurrent:3, mode:"cli"|"api" }

  - 文本类功能（report/summary、tb 分析、bug 文本、摘要）默认走 claude-proxy。

六、任务分类（文本 vs agentic）
────────────────────────────────────────────────
  - 文本类（可走中心代理）：source 为 devbench-report / 工作报告 / TB 分析 / bug 文本 /
    summarize / 规划 / commit message 等——prompt 自带全部数据，输出纯文本。
  - agentic 类（本阶段不走代理）：devbench 故事点的「执行开发/改代码」等需要工具的任务。
  - 实现：在 dispatcher / 任务对象上打 needsTools 标记；needsTools=false 才允许 claude-proxy。
    远端若把 agentic 任务指到 claude-proxy → 明确报错「该任务需本地 Claude（或等阶段1）」。

八、安全
────────────────────────────────────────────────
  - LAN_TOKEN 鉴权（Bearer），中心 claude-proxy 拒绝无 token 请求。
  - 仅监听局域网；建议绑定内网网段 / 防火墙限制来源。
  - 代理只跑「单轮文本、无工具」，不在中心机读写远端来的文件路径，杜绝越权。
  - prompt 可能含代码片段 → 局域网内可接受；如需更严可做内容审计日志。

────────────────────────────────────────────────
九、风险与取舍
────────────────────────────────────────────────
  - 单账号速率：AI 文本任务是中心串行点 → 用队列 + maxConcurrent 控制；纯脚本不占用它。
  - 能力边界：本阶段只共享「文本 AI」；真正的远端 agentic 编码要等阶段1。
  - claude -p 流式：用 --output-format stream-json 解析增量；若版本不支持则退化为整段返回。
  - 部署：每台机要能跑网关（Node/portable Node）；中心 IP/端口要固定可达。

────────────────────────────────────────────────
十、验收标准（阶段0 完成的标志）
────────────────────────────────────────────────
  1) 远端机不装/不登录 Claude，也能在本地网关里生成「工作总结报告」（实际由中心 Claude 出文本）。
  2) 远端机的 gradle/git/克隆/设备 全在本地跑，中心机 CPU 不受影响。
  3) 中心 claude-proxy 在多远端同时请求时按队列稳定出文本，不触发账号限流。
  4) agentic 编码任务被正确识别并拦截（提示本地 Claude / 阶段1），不误用中心代理。
