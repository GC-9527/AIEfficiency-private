 「钉钉机器人直接发 apk 文件到群」——自定义 webhook 机器人不支持发文件（只能 text/markdown/link/actionCard），所以没法直接把 apk 推到群里。要发文件得用钉钉企业内部应用 + 媒体上传 API（需
  appKey/secret，目前未配），而且 apk 动辄几百 MB 走钉钉也不现实。现消息里已带 UNC 目录路径，签名人按路径取包是局域网下的常规做法。这条我先不实现（除非你要配企业应用，我再接媒体上传）。我没有企业应用权限，还有其他的方案能实现吗

我先按“没有企业内部应用权限、只靠自定义机器人/CI 环境/局域网”的前提来拆可行方案，并核对一下钉钉当前机器人能力边界。

已思考 6s
可以实现“群里一键拿包”，但不能实现真正的钉钉群文件附件。没有企业应用权限时，推荐这几种：

方案 1：发下载链接，最稳
把 APK 放到内网 HTTP/Nginx、制品库、NAS Web、MinIO、OSS，再让钉钉机器人发 markdown/link/actionCard。自定义机器人官方支持 text、link、markdown、ActionCard、FeedCard 等消息类型，不是文件消息。

示例效果：

### Android 构建完成
版本：1.1.10-10110
环境：avatr8678Dev-release

[点击下载 APK](http://build-server/apk/AppMarket-xxx.apk)

UNC 路径：
\\build-server\apk\AppMarket-xxx.apk
方案 2：发内网短链 + 二维码
CI 生成一个短链，比如：

http://apk.local/r/10110
钉钉消息里放短链，签名人手机扫码或电脑点开下载。比 UNC 更适合移动端。

方案 3：接入制品库
用 Nexus、JFrog Artifactory、GitLab Package Registry、Harbor Generic Artifact、MinIO。钉钉只发“版本信息 + 下载链接 + 校验 SHA256”。这是 CI/CD 最规范的做法。

方案 4：钉钉群文件手动上传
机器人通知“包已生成”，但由有权限的人手动上传 APK 到群文件。不自动化，但不用企业应用。

方案 5：桌面自动化模拟上传，不推荐
可以用 RPA/AutoIt/Playwright 控制钉钉客户端把文件拖进群，但稳定性差、依赖登录态、容易被客户端升级打断，不适合生产流水线。

结论：你没有企业应用权限时，最佳方案是 APK 放内网下载服务/制品库，钉钉机器人发下载卡片。比把几百 MB APK 直接塞进钉钉群更稳，也更适合自动化验收报告。

2. 局域网 UNC 路径 ❌ 不能变成可点击下载
例如：

\\10.10.1.100\apk\AppMarket.apk
或者

file://10.10.1.100/apk/AppMarket.apk
钉钉不会识别成可点击链接。

原因：

钉钉只允许 http/https 链接

出于安全考虑屏蔽 file://

SMB/CIFS 协议（\server\share）无法在钉钉中直接打开

所以最终效果通常是：

这种路径：

\\192.168.200.108\PtzjShare\CarBox\Geely\E22H-GP\2026-0619\Temp_20260619\1.apk
在钉钉机器人消息里可以显示，但基本不能作为可点击下载链接。

原因：

这是 SMB/Windows共享路径（UNC Path）

钉钉只会自动识别部分 http://、https:// 链接

\\192.168.xxx.xxx\... 不会被渲染成下载链接

手机端更无法打开 SMB 共享

实际显示效果通常是：

用户只能：

手动复制

打开资源管理器

粘贴访问

不能直接点击下载。

如果是 Windows PC 用户
有个折中方案：

file://192.168.200.108/PtzjShare/CarBox/Geely/E22H-GP/2026-0619/Temp_20260619/1.apk

钉钉通常不会把 file:// 渲染成可点击链接

手机端完全无效

最好的方案
在这台机器上起一个 HTTP 服务：

假设 APK 实际在：

D:\PtzjShare\CarBox\Geely\E22H-GP\2026-0619\Temp_20260619\1.apk
用 Nginx 映射：

location /apk/ {
    alias D:/PtzjShare/;
}
那么下载地址变成：
