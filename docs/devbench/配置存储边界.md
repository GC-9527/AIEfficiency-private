# DevBench 配置存储边界

## 结论

DevBench 采用三层存储，不把运行时变化拆到更多受 Git 跟踪的 JSON 文件：

| 数据层 | 位置 | 数据范围 | 同步方式 |
|---|---|---|---|
| 只读启动种子 | `configs/market-projects.json` | 安全、可移植的默认仓库定义 | 仅随 Git/安装包分发；运行时禁止写入 |
| 团队共享运行态 | SQLite `devbench_userdata` 的 `__devbench_shared__/shared` | 仓库定义、车型、关键词、状态、钉钉、经验、训练、RAG、共享版本与操作日志 | Gateway shared-bundle/gossip；Service Control 只同步数据库 |
| 本机私有配置 | `configs/local/devbench-projects.json` | 本机工程路径、克隆父目录、仓库到本机 checkout 的绑定 | 不进 Git、不自动跨机同步；使用工程配置页备份/还原 |

拆成多个受 Git 跟踪的运行时配置文件只能把冲突分散到多个文件，无法消除用户交互、跨节点同步和整文件序列化产生的冲突，因此不采用。

## 写入规则

- `market-projects.json` 只在共享数据库没有初始化时读取一次；迁移不得清洗、排序或回写源文件。
- 仓库定义增删改、车型配置导入、钉钉设置、AI 人工纠正、RAG 实际值替换、共享备份恢复和 gossip 合并都只写 SQLite。
- 本机工程增删改、克隆父目录和本机匹配记忆只写 ignored 本机配置。
- Service Control 不复制 `market-projects.json`，也不自动复制本机配置。数据库内容相同的同步必须返回 `updated:false`，不得提高共享版本。
- Git 跟踪文件由开发者通过 Git 显式维护，运行中进程不得把数据库快照镜像回仓库。

## 兼容与演进

- 旧配置中的 `projects`、`cloneParent` 首次读取后复制到本机配置，旧文件字节保持不变。
- 旧配置中的顶层 `vehicleMap`、`keywordMappings` 和共享字段只迁入 SQLite，旧文件字节保持不变；本机 `__system__/marketProjectsRuntimeSeedV1` 标记保证兼容补导只执行一次，恢复屏障或既有操作历史会阻止旧值复活。
- 现阶段沿用已有共享快照和增量操作协议，先消除双写和 Git 冲突。若共享行持续增长到影响写入或同步，再按 `registry`、`project:<id>`、`ops` 拆成多行或关系表；这属于数据库内部演进，不改变三层边界。

## 回归门禁

涉及上述配置交互的测试必须保存种子文件原始文本或 SHA-256，并在操作完成后断言逐字不变；同时验证 SQLite 中的业务结果和共享版本是否按语义变化。
