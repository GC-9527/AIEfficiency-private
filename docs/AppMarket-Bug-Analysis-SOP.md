# 《AppMarket 应用 Bug 分析标准流程 SOP v1.0》

> 📌 **本文档定位**：一套**端到端、可复用、可度量**的 Bug 分析标准作业流程（Standard Operating Procedure）。任何 Bug 走完此流程都能得到**一致、可追溯、可闭环**的分析结论。
>
> **适用对象**：AAOS AppMarket 类应用的全生命周期 Bug 处理
> **核心原则**：**每个阶段都有入口、活动、产出、出口、工具、SLA**

## 2. 八大阶段流程定义

> 每个阶段都采用统一格式：**入口 → 活动 → 产出 → 出口 → 工具 → SLA**

---

### 2.1 Stage 1 — INTAKE（接单）

| 字段 | 内容 |
|------|------|
| **入口条件** | 任何渠道收到 Bug 线索（用户投诉 / 测试单 / 崩溃上报 / 车主反馈） |
| **核心活动** | ① 登记工单 ② 字段补全 ③ 去重检查 ④ 初步标签 |
| **产出物** | **工单 (Ticket)**：含 ID、标题、来源、原始描述、附件清单 |
| **出口条件** | 工单字段齐全 + 无重复单 |
| **工具** | Jira / 禅道 / 飞书工单 / Bug 平台 |
| **SLA** | ≤ 10 分钟 |
| **责任人** | TL |

**必填字段清单**：
```
□ 工单 ID        □ 标题（≤30字）     □ 来源渠道
□ 上报时间       □ 上报人           □ 设备型号
□ App 版本       □ 原始描述         □ 附件数量
□ 是否疑似重复   □ 去重引用单号
```

---

### 2.2 Stage 2 — TRIAGE（分诊）

| 字段 | 内容 |
|------|------|
| **入口条件** | Intake 完成的工单 |
| **核心活动** | ① 严重度评级 ② 一级分类 ③ 分配责任人 ④ SLA 设定 |
| **产出物** | **分诊标签**：P 级 + 分类代号 + 负责人 |
| **出口条件** | 所有字段打标完成 |
| **工具** | 严重度矩阵（见下）+ 分类体系 |
| **SLA** | ≤ 30 分钟 |
| **责任人** | TL |

**严重度评定矩阵**：

| 严重度 | 定义 | 示例 | 响应 SLA |
|-------|------|------|---------|
| **P0** | 阻塞/数据丢失/安全 | 全量闪退、数据错乱、隐私泄漏 | 1h 分析 + 4h 修复 |
| **P1** | 核心功能不可用 | 无法下载/安装/登录 | 4h 分析 + 24h 修复 |
| **P2** | 部分功能异常 | 特定场景卡顿、偶现错误 | 1d 分析 + 3d 修复 |
| **P3** | 体验/优化 | UI 细节、文案错误 | 3d 分析 + 迭代修复 |

**分类标签**（见辅助手册 §2 的 23 类代号）

### 2.3 Stage 3 — EVIDENCE（证据采集）

| 字段 | 内容 |
|------|------|
| **入口条件** | 已分配的工单 |
| **核心活动** | ① 日志采集 ② 视频/截图 ③ 环境快照 ④ 用户行为轨迹 |
| **产出物** | **证据包（Evidence Package）** |
| **出口条件** | 证据包通过完整性检查 |
| **工具** | ADB / bugreport / scrcpy / 崩溃平台 / 埋点 |
| **SLA** | ≤ 1 小时 |
| **责任人** | AE |

**证据包标准清单**：
```
evidence_<工单ID>/
├── logs/
│   ├── logcat_full.log          # 全量 logcat
│   ├── logcat_app.log           # 按包名过滤
│   ├── anr_traces.txt           # ANR trace（如有）
│   ├── tombstone_*.txt          # Native crash（如有）
│   └── dmesg.log                # 内核日志
├── media/
│   ├── repro_video.mp4          # 复现视频
│   └── screenshots/             # 关键截图
├── env/
│   ├── build_prop.txt           # 设备信息
│   ├── dumpsys_meminfo.txt      # 内存
│   ├── dumpsys_activity.txt     # Activity 栈
│   └── pm_list_packages.txt     # 包列表
├── app/
│   ├── apk_info.txt             # 版本/签名
│   └── shared_prefs_backup/     # 如需
└── meta.json                    # 证据清单索引
```

**完整性检查 Checklist**：
- [ ] logcat 覆盖异常发生前 30s 及后 10s
- [ ] 视频清晰展示操作 → 异常全过程
- [ ] 环境快照 5 项齐全
- [ ] meta.json 填写完整

### 2.4 Stage 4 — REPRO（复现验证）

| 字段 | 内容 |
|------|------|
| **入口条件** | 证据包齐全 |
| **核心活动** | ① 按报告步骤复现 ② 确定稳定性 ③ 最小化复现路径 |
| **产出物** | **复现报告**：复现率 + 最小步骤 + 触发条件 |
| **出口条件** | 复现率 ≥ 50% 或 明确标注"无法复现" |
| **工具** | ADB 脚本 / UIAutomator / 测试机矩阵 |
| **SLA** | ≤ 2 小时 |
| **责任人** | AE + QA |

**复现分级**：

| 级别 | 复现率 | 后续路径 |
|------|-------|---------|
| **必现** | 100% | 直接进入 Analysis |
| **高频** | 50-99% | 进入 Analysis + 记录触发条件 |
| **偶现** | 10-49% | 加埋点 + 长压测 |
| **罕见** | <10% | 转 Monitor（埋监控待重现） |
| **不可复现** | 0% | 走异常路径（§7） |

**最小复现路径产出模板**：
```
前置条件:
  - 设备: XX 型号
  - 版本: XX
  - 状态: 已登录 / 首次启动 / ...

最短步骤:
  1. ...
  2. ...
  3. ...
触发条件: 车速 > 5km/h / 网络断开 / ...
预期: ...
实际: ...
复现率: N/M
```

### 2.5 Stage 5 — ANALYSIS（根因分析）

| 字段 | 内容 |
|------|------|
| **入口条件** | 复现报告 + 证据包 |
| **核心活动** | ① 决策树分类 ② 日志关键词扫描 ③ 时间线重建 ④ 根因假设 ⑤ 假设验证 |
| **产出物** | **根因分析报告**（含直接原因 + 根本原因 + 归类） |
| **出口条件** | 根因被证据支撑（非猜测） |
| **工具** | AI 助手（/bug-report skill） / GraphRAG / 辅助手册 |
| **SLA** | P0: 1h / P1: 4h / P2: 1d / P3: 3d |
| **责任人** | AE + AI |

**标准分析六步法**：

```
1. 分类 ───▶ 用决策树判断类型（UI/FUNC/DRIVE/...）
2. 定性 ───▶ 用四象限矩阵判代码/环境/其他
3. 扫日志 ─▶ FATAL > ANR > Exception > WARN
4. 建时间线 ▶ 事件表（时间 | 事件 | 说明）
5. 提假设 ─▶ 至少 2 个候选根因
6. 验证 ───▶ 每个假设用证据确认/排除
```

**根因报告标准模板**：

```markdown
## 根因分析

### 现象（来自视频+日志）
...

### 分类
- 一级: [FUNC-01]
- 层级: 集成层
- 性质: 代码错误

### 关键证据
1. logcat 行 1234: NullPointerException at XXX:87
2. 视频 00:15: 点击 XX 按钮后黑屏
3. dumpsys: Activity 栈异常

### 候选假设
- H1: XXX 未初始化（✅ 证据 1 支持）
- H2: 网络超时（❌ 证据 2 排除）

### 确认根因
- 直接原因: XXX 对象在 onResume 前被使用
- 根本原因: 生命周期回调顺序假设错误

### 影响评估
- 影响范围: 100% 用户
- 数据安全: 无影响
```

**知识库条目模板**（供未来相似 Bug 检索）：

```markdown
## 修复套路
在 onCreate 初始化 + 空值防御

## 相关工单
#1234, #5678
```

## 3. 决策门（Gates）

每个阶段之间设置**硬门禁**，不满足条件不得前进：

| Gate | 位置 | 检查项 | 不通过动作 |
|------|------|--------|-----------|
| **G1** | Intake → Triage | 工单字段齐全 | 回退补全 |
| **G2** | Triage → Evidence | P 级+分类已打标 | 回退重评 |
| **G3** | Evidence → Repro | 证据包完整性检查通过 | 补采证据 |
| **G4** | Repro → Analysis | 复现率明确 | 走异常路径 |
| **G5** | Analysis → Review | 根因有证据支撑 | 重新分析 |
| **G6** | Review → Fix | TR 签字 | 方案重议 |
| **G7** | Fix → Close | 验证通过 + 回归通过 | 打回修复 |

## 6. SLA 与度量指标

### 6.1 全流程 SLA 汇总

| P 级 | Intake→Repro | Analysis | Fix | Total |
|------|-------------|----------|-----|-------|
| P0 | 3h | 1h | 4h | **8h** |
| P1 | 3h | 4h | 24h | **31h** |
| P2 | 3h | 1d | 3d | **~4d** |
| P3 | 3h | 3d | 迭代 | **迭代级** |

### 6.2 核心度量指标（KPI）

```
效率类:
  MTTR (平均修复时间)
  MTTD (平均定位时间)
  Stage-wise cycle time

质量类:
  一次修复通过率（Review 无打回）
  回归率（同 Bug 30 天内再发生）
  误分诊率

沉淀类:
  知识库命中率（新 Bug 通过检索获得线索）
  流程成熟度（各阶段 Gate 通过率）
```

## 7. 异常路径处理

### 7.1 无法复现

```
Repro 阶段复现率 = 0
  ↓
分叉 A: 证据充分 → Analysis 仅凭日志分析（标注"低置信度"）
分叉 B: 证据不足 → Monitor 模式
              - 加埋点 / 崩溃上报字段补全
              - 设定监控窗口（默认 30 天）
              - 到期未重现 → 关闭"无法复现"
              - 重现 → 重入 Analysis
```

### 7.2 根因无法确定

```
Analysis 阶段达到 SLA 仍未定位
  ↓
升级机制:
  - 拉入 TR 共同分析
  - 必要时联系上游（OEM/Framework 团队）
  - 评估是否降级为"规避方案"
```

### 7.3 方案评审无法决议

```
Review 无共识
  ↓
  - 升级到更高级别决策者
  - 或先上小流量灰度
  - 或采用"保守方案 + 后续优化"
```

### 7.4 修复引入新问题

```
Verify 阶段发现回归
  ↓
  - 立即回滚
  - 新 Bug 开工单进入流程
  - 原 Bug 状态回退到 Review
  - 记录到"流程改进库"
```
