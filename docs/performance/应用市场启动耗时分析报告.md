# 应用市场启动耗时分析报告

> **分析对象**：车机端 **应用市场（com.appmarket.automotive）** 的启动过程（avatr8155、avatr8678、f515R、gwmx9）
>
> **测试条件**：重启车机 → 系统稳定后 → 点击图标计时
>
> **时间**：2026‑05‑28
>
> **指标**：冷启动 < 0.8 秒



## 一、结论

| 车型 | 冷启动（点开 → 首页可见） | 指标 | 主要瓶颈 |
|------|--------------------------|----------|----------|
| **f515R** | **≈ 2.3 秒** | <0.85s | 缺少细粒度埋点，无法精准定位 |
| **avatr8678** | **≈ 2.6 秒** | <0.80s | 首页图片单张仍需 ~0.6 秒 |
| **avatr8155** | **≈ 2.8 秒** | <0.80s | 联网拉配置略慢（1.3 秒） |
| **gwmx9** | **≈ 4.4 秒** | <0.85s | HomeActivity 首帧渲染偏慢 + 配置接口 1.7 秒 |

- 四台冷启动 **2.27 ~ 4.37 秒**，全部超 0.8 秒指标 2.8 ~ 5.5 倍。
- 共性大头是 **② 配置接口请求时长**：四台均要等海外后端 `api.marketapply.com` 把启动配置取回来才创建首页，单这段就占 1.0 ~ 2.5 秒。
- 车机之间差异主要来自 **HomeActivity 首帧渲染**（gwmx9 0.84 s vs avatr8678 0.24 s）+ **网络链路质量**（gwmx9 TLS 握手 456 ms 最慢）。
- DNS 不是瓶颈（10 ~ 22 ms，占比 ≤ 1.5%）。

## 三、原因及分析

### 3.1 ② 配置接口请求（共性大头）

四车型 ② 段均要 1.0 ~ 2.5 秒，几乎被 `refreshAppConfig` 网络请求占满。原因：

1. **后端在海外公网**（`api.marketapply.com`）：跨境 DNS + TCP + TLS 握手 + 数据往返。三车型实测建连成本 0.53 ~ 0.86 秒（gwmx9 链路最差 0.86 s），加上跨境传输，配置端到端 1.34 ~ 2.02 秒。
2. **同步阻塞**：处在"点击 → 首页"必经路径，`MainActivity.onAfterViews()` 发起配置后用协程 `await` 等返回，网络一慢就锁住整条冷启动。
3. **按语言下发**：avatr8155 取葡语、avatr8678 取英语、gwmx9 取中文，但同一套海外后端，耗时量级一致。

### 3.2 ①③ 渲染（车机差异主因）

纯本地渲染，最体现设备性能：

| 车型 | ① Logo 首帧 | ③ 首页骨架首帧 |
|------|------------|----------------|
| avatr8678 | 802ms | **236ms** |
| f515R | 699ms | 483ms |
| avatr8155 | 1127ms | 391ms |
| gwmx9 | 1030ms | **838ms** |

- **gwmx9 ③ 838ms** 显著高于其他车型（avatr8678 仅 236ms），是它总耗时最高的渲染侧主因，与中端芯片渲染能力相关。
- **avatr8155 ① 1127ms 较高**，与 Logo 动图首次解码 + 图形环境首次建立有关。

### 3.3 拉首页内容 + 图片（HomeActivity 启动之后）

HomeActivity 创建后再请求 `getHomeData / packageListV3 / getAppInfoByPkgsV3`（约 0.38 ~ 0.43 秒），再逐张下载图标。原因：

1. **二次跨公网**：内容接口虽走 h2 复用连接（避免重新建连），但仍要跨境往返 0.4 秒级。
2. **海外 CDN 图片**：图标来自海外 `static.marketapply.com`，单图远程下载 348 ~ 614 ms；avatr8678 已改为并发 DNS（5 路同时解析，8 ~ 20 ms 内全部完成），但 HTTP 下载本身仍要 0.4 ~ 0.6 秒。
3. **缓存命中后近 0 ms**：图片二次访问 0 ~ 3 ms 即可，问题在于首次必须联网。

### 3.4 DNS 与网络观察

1. **DNS 单次解析非常快（10 ~ 22ms）**，本身不是性能瓶颈。
3. **时间较长的是 DNS 之后的 TLS 握手**：avatr8155 TLS 301ms，avatr8678 338ms，gwmx9 456ms（链路最差）。
4. **avatr8678 用了并发 DNS**：5 张图片并发查 DNS，8 ~ 20 ms 内全部完成，是一个值得保留的设计。

### 3.5 各车型瓶颈拆解

#### 1️⃣ f515R（最快，但黑盒）
- **优势**：从点开到首页可见仅 **2.3 秒**。
- **风险**：这版 App 用了**加密日志**（`ELOG|…`），看不到细分耗时，相当于"快但不知道为什么快"。
- **隐患**：万一某天变慢，**没有埋点就排查不了**。

#### 2️⃣ avatr8155（较快，体验良好）
- **冷启动总耗时**：~2.8 秒。
- **主要耗时点（含日志佐证）**：
  - 联网拉配置 1.3 秒 — `L7495: refreshAppConfig success cost=1335ms`
    - 其中 **TLS 握手 301ms** — `L6727: tlsHandshake tlsCost=301,2ms`
    - **首字节 1054ms** — `L7193: firstByte sinceCallStart=1054,6ms`
  - MainActivity 显示首帧 1.1 秒 — `L6803: Displayed MainActivity: +1s122ms`
  - 首页图片远程下载 348‑480ms — `L9586: GlideImageLoader cost=348ms from=REMOTE`
- **整体健康度高**，几乎没有主线程卡顿（无 MainThreadMonitor 警告）。

#### 3️⃣ avatr8678（良好水平）
- **冷启动总耗时**：~2.6 秒。
- **主要特征（含日志佐证）**：
  - 单图远程下载 397‑614ms — `L44067: GlideImageLoader cost=397ms from=REMOTE`。
  - 配置接口 1 680‑2 016ms — `L40454: refreshAppConfig success cost=1680ms`。
  - 主线程零阻塞：**0 次 MainThreadMonitor 警告**。
  - 本地存储 MMKV 仅 3ms — `L35610: core.mmkv cost=3ms`。
  - DNS 并发解析：5 张图片并发查 DNS，8‑20ms 内全部完成 — `L43572‑L43585`。
- **仍可继续优化的点**：
  - TLS 握手 338ms — `L37994: tlsHandshake tlsCost=338.2ms`，可加链接预建/会话复用。
  - 首页 6 张图片 HTTP 请求 397‑614ms，可预置或缓存。
- **结论**：跻身良好水平，仅差 0.3 秒可追平 f515R。

#### 4️⃣ gwmx9（较慢）
- **冷启动总耗时**：**~4.4 秒**（用户点击 `20:26:13.298` → HomeActivity 首帧 `20:26:17.670`）。
- **拆解**：
  - 用户点击 → MainActivity START：5ms（系统调度，正常）
  - MainActivity START → Displayed：**1025ms**
  - MainActivity → HomeActivity START：2.5s（含业务逻辑等配置）
  - HomeActivity START → Displayed：**838ms**
- **主要耗时点（含日志佐证）**：
  - 配置接口 **1737ms** — `L13751: refreshAppConfig success`，比 avatr8155(1335ms) 慢约 400ms。
  - HomeActivity 首帧 **838ms**，较 avatr8155 的 +390ms 偏慢约 1 倍，与芯片渲染能力相关。
  - MainActivity 首帧 **1025ms**，与 avatr8155 同水平。
- **特征**：
  - 无 Choreographer 跳帧、无 MainThreadMonitor 阻塞，主线程健康。
  - 跨境链路最差：TLS 握手 456ms（avatr 系列 301‑338ms），是配置时间偏长的主因。

### 3.6 关键耗时点排名（跨车型综合）

| 排名 | 耗时项 | 出现车型 | 平均耗时 | 严重程度 |
|------|--------|----------|----------|----------|
| 1 | **配置接口 refreshAppConfig** | 四车型 | 1.3‑2.0s | 中等 |
| 2 | **HomeActivity 首帧渲染** | gwmx9 | 838ms | 中等（中端芯片渲染慢） |
| 3 | **首页图片串行下载** | avatr8155 / avatr8678 | 350‑600ms/张 | 中等 |
| 4 | **TLS 握手** | 三车型 | 250‑450ms | 轻微 |



## 四、优化方案

### 4.1 通用优化方案

1. **首页"先看到再说"——骨架屏 + 本地缓存优先**
   - 用户打开 App 时，先用上次记住的旧数据立刻显示首页，**不要等网络回来才画**。
   - 等接口回来再悄悄替换内容，用户感知"瞬开"。

2. **图片预下载与本地预置**
   - 把常用图标/Banner 打包到 App 安装包里。
   - 已下载的图片可永久保留，目前看 **MEMORY_CACHE 命中只要 0‑3ms**，能解决图片慢问题。

3. **启动时只做"必须做"的事**
   - `biz.appconfig` 拆成"必要"和"非必要"两部分，非必要的延迟到首页显示之后再跑。
   - 把所有非阻塞的初始化挪到子线程，**主线程禁止做任何 IO 和加解密**。

4. **DNS 预热 + TLS 链接预建**
   - 在 Application.onCreate 子线程里，对核心域名（`api.marketapply.com`、`static.marketapply.com`）发起一次空请求，或者系统提前解析。**把 DNS 缓存暖好 + TLS 链接建好**。
   - 实测可省 **DNS ~20ms + TLS ~300‑450ms ≈ 350ms 起步**。gwmx9 链路差的场景受益最明显。

### 4.2 优化预期效果

| 车型 | 当前冷启动 | 目标冷启动 | 关键动作 |
|------|------------|------------|----------|
| f515R | 2.3s | **保持 < 2.5s** | 补埋点防回退 |
| avatr8678 | 2.6s | **< 2.0s** | 配置缓存优先 + 图片并发/预置 |
| avatr8155 | 2.8s | **< 2.0s** | 缓存优先 + 接口合并 |
| gwmx9 | 4.4s | **< 2s** | 缓存优先 + HomeActivity 渲染优化 + TLS 链接预建 |
