# AI 工作台产品概述

## 产品目标

AI 工作台（`/aiautowork`）是 DevBench 之前的统一任务入口和调度控制面。它把 TB 单、手工任务、Git Code Review 统一抽象为故事点草稿，负责识别、配置推导、确定性预检、有限次数自动修复、人工纠错、批量创建和执行排队。

原 `/devbench` 保留为单个故事点的深度工作区，继续承载完整对话、代码修改、Review、构建、测试、验收与报告。AI 工作台不复制这些深度能力，只提供摘要和进入入口。

本阶段只交付 Mock UI、UX、设计文档和高保真交互 Demo，不接入真实 TB、Git、AI、数据库、设备或任务调度。

## 产品边界

| AI 工作台负责 | DevBench 负责 | Mock Demo 不负责 |
|---|---|---|
| 创建任务草稿 | 单故事点完整上下文 | 真实故事点创建 |
| 单个与批量输入 | 代码修改与工具执行 | 真实 AI 推导 |
| 配置候选与人工确认 | 编译、测试与验收 | 真实 Git/Worktree |
| 批量异常处理 | 报告与交付 | 后端、数据库、鉴权 |
| 创建结果与执行排队 | 故事点内持续协作 | 生产队列与通知 |
| 并发和策略设置 | 具体开发工作流 | TB 状态写入 |

## 用户角色

### 普通研发人员

- 创建单个 TB、手工任务或 Git Review。
- 查看自己的进行中、待办和等待人工项。
- 处理 AI 无法确定的少量配置。
- 从摘要进入 DevBench。

### 高级研发人员

- 批量导入最多 100 条混合任务。
- 处理多工程、多仓库、不同分支和多个 Flavor。
- 比较 AI 候选与最终生效配置。
- 使用历史成功配置、模板和批量补全。

### 技术负责人

- 查看全部运行、排队、失败和阻塞。
- 调整优先级和队列位置。
- 审核高风险配置、Critical Findings 和批量分组。
- 区分“已创建”与“正在执行”。

### 平台管理员

- 设置四类并发：配置推导、配置校验、Reviewer、故事点执行。
- 配置自动通过、人工确认和自动修复策略。
- 管理 TB 数据来源、工程/仓库/Flavor 映射和设备资源。
- 重置 Demo 场景。

## 核心使用场景

1. 输入 `CARB-13465`，完成 TB 解析、配置推导、预检并创建故事点。
2. 输入一段研发需求，AI 生成标题和候选工程，用户只确认不确定字段。
3. 输入 commit、范围、分支、MR 或自然语言，创建 Git Review 草稿。
4. 粘贴 100 条混合输入，系统自动分流，用户只处理 8 条异常和 17 条组确认。
5. AI 连续三次自动修复仍失败，回到评分更高的 V1 并要求补充分支。
6. 已创建 100 个故事点，但最大执行并发为 5：页面显示运行 5、等待 95。

## 统一故事点来源

| 来源 | 标识 | 必要信息 |
|---|---|---|
| TB 单 | `TB` + 链接图标 | TB 单号、标题、项目、负责人 |
| 手工任务 | `MANUAL` + 文档图标 | 用户原文、AI 生成标题、关联工程 |
| Git Review | `GIT_REVIEW` + 分支图标 | 仓库、Review 类型、Base/Head/Revision |

来源同时使用图标、文本和标签表达，不依赖颜色。

## 产品成功标准

- 用户进入工作台 5 秒内可识别当前最紧急事项。
- 100 条批量任务不出现 100 次逐项确认。
- 高分不能掩盖关键字段低分。
- 创建状态和执行状态始终分离。
- AI 推导始终标记为候选，不伪装为事实。
- 用户明确输入和人工锁定字段不会被自动修复覆盖。
- 所有主要操作均有 Mock 反馈。
