# 工作流与风险分级

## 1. 先区分任务类型

| 类型 | 首要目标 | 默认范围 | 最低模式 |
|---|---|---|---|
| BUG 修复 | 最小改动修根因，防止同类回归 | 缺陷链路 + 共享消费者 | standard |
| 新功能 | 完整契约和状态覆盖 | 前端、API、权限、数据、验收 | standard |
| UI/UX 调整 | 视觉与交互一致，不破坏关联页面 | 直接页 + App shell + 相邻路由 | standard |
| 全局样式/共享壳 | 控制爆炸半径 | 全部关键路由和视口 | deep |
| 性能治理 | 可重复的差异数据 | 构建包体 + 冷/暖浏览器 | deep |
| 安全/权限/数据库 | 不降低边界并保证兼容 | 前后端、迁移、回滚 | deep |
| 代码评审 | 找出新增风险和证据缺口 | diff + 反向依赖 | standard |

## 2. 风险评分

每项命中加分，取最高风险而非平均：

- +5：全局 CSS、App/Layout、路由入口、认证、请求公共层、数据库迁移、安全边界。
- +4：Dialog/Portal/Drawer、Sidebar、FloatingDock、Toast、共享表格/表单、WebSocket。
- +3：三个及以上路由消费的组件、轮询、缓存、懒加载、动态导入、状态机。
- +2：单路由复杂交互、表格、长表单、拖拽、文件上传。
- +1：局部文案、非共享样式、测试代码。

建议：0–2 quick；3–5 standard；6+ deep。任意 +5 项直接 deep。

## 3. 影响图必须回答的问题

1. 变更由哪个用户动作触发？
2. 入口路由、共享壳、组件、服务、API、数据库分别在哪里？
3. 哪些文件反向依赖了改动文件？
4. 哪些组件共享同一 CSS token、Portal root、scroll container 或 z-index 层？
5. 哪些路由与改动路由共享 App shell、导航、悬浮层、请求层？
6. 哪些状态可能被改变：加载、空、错误、权限、慢请求、断线、重试？
7. 能否回滚？数据库/数据格式是否向后兼容？

## 4. 变更前证据

- Git 状态与基线 ref。
- 当前页面截图或已有基线。
- 当前关键测试和构建结果；若已有失败，明确“基线失败”。
- 当前包体和浏览器指标；缺基线时先记录，不立即把当前状态宣告为正确。
- 当前用户改动不得被清理、覆盖或混入本任务提交。

## 5. 实现策略

- 先写一条能复现问题或表达契约的测试/场景，再修改实现。
- 共享根因只修一次；页面特例必须有明确产品差异，不能复制补丁。
- 对超大文件优先抽离纯函数、状态模型或可测试组件，但不要把局部修复扩大成无关重构。
- 兼容旧数据和旧调用方；破坏性变更必须明确版本与迁移路径。
- 对异步行为使用请求序号、AbortController、幂等键或状态机，防止竞态。

## 6. 验证顺序

1. 语法/类型/静态规则。
2. 与变更最接近的单元或模型测试。
3. 模块测试和构建。
4. API/数据库/权限集成测试。
5. 影响路由浏览器几何与交互检查。
6. 视觉基线与性能差异。
7. Git diff 复核：是否有调试代码、生成物、秘密、重复实现、无关格式化。

越早失败越早停止，修复后从失败层开始，再补跑其后的受影响层；不必无脑重跑完全无关的高成本测试。

## 7. 完成定义

“代码写完”不是完成。只有满足以下条件才可交付：

- 需求和根因均被覆盖。
- 影响图中的关键路径已有测试或浏览器证据。
- 新增 P0/P1 为零。
- 性能未越过预算，或有经过明确批准的例外。
- 未执行项和残余风险清楚列出。
- 没有通过更新基线、吞错、提高 z-index 或关闭检查掩盖问题。
