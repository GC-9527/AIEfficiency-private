# 多 AI、无人值守与可续作协议

## 角色边界

### Root Agent

负责：

- 需求语义、仓库/分支/Flavor 选择；
- 架构、不变量、安全与风险决定；
- PREWRITE 批准、范围变更和最终验收；
- 对用户和工单输出真实结果。

### Worker Agent

只能接收边界清晰的任务：

- 指定目标、文件预算、禁止范围、输入证据和验收命令；
- 不重新定义业务目标；
- 不改变公共合同或扩大模块范围；
- 新证据与计划冲突时停止并回报 Root。

共享工作区同一时间最多一个可写 Agent。并行 Agent 应使用独立 worktree，或全部只读。

## 低 Token 阶段

建议编排：

1. `TRIAGE`：判断是否触发、风险初判、定位最小证据；
2. `DIAGNOSE_PLAN`：形成 PREWRITE 决策记录；
3. `REPAIR`：仅执行已批准方案；
4. `VERIFY_EXECUTE`：运行目标测试并检查 diff；
5. `INDEPENDENT_REVIEW`：高风险或共享合同变更时执行；
6. `REPORT_SHORT` / `REPORT_EXPERT`；
7. `MEMORY_DISTILL`：只沉淀验证事实和被拒绝方案。

确定性步骤交给脚本：Git 状态、JSON 校验、文件范围、重复源码、测试退出码。不要让模型反复描述这些机械事实。

## 无人值守策略

- LOW/MEDIUM：在预算内选择安全、附加、可逆默认方案；
- HIGH/CRITICAL：缺授权或证据时生成 `BLOCKED_NEEDS_DECISION`，不修改代码；
- 测试失败：基于具体失败修复一次，再重新跑受影响测试；不得无限循环；
- 连续失败或范围扩大：写入交接状态并停止；
- 外部写入、发布和破坏性动作始终需要明确策略授权。

## 交接最小状态

交接必须包含：

- task_id、目标、非目标、风险与权限；
- repo、branch、HEAD、dirty patch hash；
- Variant/Flavor/车型/环境；
- VERIFIED/INFERRED/UNKNOWN；
- 不变量、候选方案、已选方案和禁止结果；
- 实际改动、测试命令、结果和残余风险；
- 下一步只列一个最小动作。

接手者首先重新运行 Git 状态和差异检查；动态事实不得只依赖旧交接。

## 失败与重试

- Worker 失败后，Root 必须提供具体失败证据，不能只说“再认真检查”；
- 修复只针对失败点和其回归半径；
- 新模型接手时不重复全量扫描，先验证交接中的关键锚点；
- 已被证据否定的方案写入 `rejected_options`，避免下一 AI 重走。
