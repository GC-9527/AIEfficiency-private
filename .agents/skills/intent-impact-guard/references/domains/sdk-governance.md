# SDK 治理与单一源码检查表

## canonical 源定位

修改前必须证明：

- `sdk-api` 的合同位置；
- 目标厂商/车型实现 `sdk-xxx-impl`；
- 应用市场工程如何通过源码依赖、AAR 或发布仓库接入；
- 当前分支/Flavor 是否仍引用旧源码；
- 第三方 jar/aar/libs、版本号和打包链。

无法定位 canonical 源时保持只读，禁止在应用工程复制一份“临时修复”。

## 交付结构

目标交付物通常只允许：

- `sdk-api-<version>`；
- `sdk-<vendor-or-model>-impl-<version>`；
- 对应 docs/车型目录下的文档、截图、日志、图文影音说明；
- 版本、依赖、混淆、兼容和测试证据。

应用市场工程只能依赖交付物或正式源码模块，不保存第二份 SDK 业务源码。

## 迁移与删除

删除旧 SDK 前必须证明：

- 所有目标分支、Flavor、车型已切换；
- 编译依赖和运行时加载均指向新实现；
- API、资源、Manifest、ProGuard/R8、ABI 兼容；
- AppMock/测试适配完成；
- 回滚版本和接入文档可用。

“某个 Flavor 已接入”不能推断“全部可删除”。

## 新能力与修复

- 先判断能力属于公共 API、厂商实现还是车型配置；
- 不把厂商差异泄漏到 `sdk-api`；
- 共用同一厂商 impl 的车型用配置目录区分；
- 关注 callback 线程、生命周期、内存泄漏和异常隔离；
- 版本号遵循兼容语义，调用方必须可定位真实版本；
- 修改后构建目标 SDK，并至少编译一个真实应用调用方。

## AI 禁止动作

- 修改应用壳中的废弃 SDK 源码；
- 在其他分支/Flavor复制 SDK 源码；
- 为赶进度创建第二个同名 impl；
- 把第三方二进制反编译源码当 canonical；
- 未核对车型复用关系就拆分或合并实现；
- 只改文档或版本号而未验证真实打包内容。
