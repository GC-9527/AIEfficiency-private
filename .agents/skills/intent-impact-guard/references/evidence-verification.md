# 证据与验证协议

## 证据格式

```text
VERIFIED path:locator — 直接观察到的事实
INFERRED 依据 — 推断及其前提
UNKNOWN 需要什么证据才能确认
```

`locator` 可以是行号、符号、路由键、Gradle task、测试名、日志时间或 Commit SHA。不要捏造行号。

## 最小充分证据

### UI/入口问题

- 入口组件或导航配置；
- 目标页面/路由；
- 相关状态或权限守卫；
- 至少一个已有测试或可执行行为。

### SDK/API 问题

- canonical 模块和依赖关系；
- API 定义与实现；
- 至少一个调用方；
- Variant/Flavor/车型覆盖；
- 打包与版本合同。

### Android 生命周期问题

- 创建/注册/启动点；
- 释放/取消/注销点；
- 所属 lifecycle 和线程；
- 重建、后台、异常路径。

## 验证层级

按成本递增：

1. 静态范围检查：diff、类型、lint、依赖方向；
2. 目标单元/组件测试；
3. 受影响模块构建；
4. 关键集成/契约测试；
5. 运行态验证：浏览器、设备、AppMock、ADB/API；
6. 跨 Variant/Flavor/车型或部署环境验证。

低风险不必跑全量测试，但必须覆盖目标和不变量。高风险不能只靠 lint/编译声称完成。

## 真实性规则

- 只有工具实际返回成功，才能写 `PASS`；
- “代码看起来正确”不是测试证据；
- “建议运行”必须记为 `NOT_RUN`；
- 失败不能被后续无关成功覆盖；
- 截断日志需保留命令、退出码和关键错误；
- 当前分支/HEAD/Dirty Patch 变化后，旧验证结论失效或需重新确认。

## 回归半径

从改动点沿以下边展开，直到稳定合同边界：

- 路由/导航 → 认证状态 → 权限守卫 → 目标页 → 登录回跳；
- 公共组件 → 所有调用页 → 断点/主题/状态；
- SDK API → 实现 → 调用 App → Flavor/车型 → 打包；
- 数据源 → 缓存/Mock/回退 → 展示 → 错误处理；
- Android 注册点 → 生命周期 → 线程/协程 → 释放点。

记录“为什么到此停止”，避免无边界全仓扫描。
